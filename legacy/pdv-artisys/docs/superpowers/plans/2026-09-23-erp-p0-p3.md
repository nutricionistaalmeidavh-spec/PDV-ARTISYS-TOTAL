# ERP P0-P3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implementar no PDV ArtiSys a base gerencial P0, gestão empresarial P1, bancos/conciliação P2 e automação financeira P3, preservando os serviços canônicos existentes e exigindo E2E Electron real para cada capacidade.

**Architecture:** `finance-service.js`, vendas, compras, caixa, EventBus/outbox, auditoria, backup e importação atuais continuam autoritativos. As novas capacidades entram em serviços focados para dimensões gerenciais, reporting, extratos/conciliação e recorrências/alertas; projeções são somente leitura e nenhuma conciliação baixa conta sem confirmação. A UI segue `operational-pages.js`/`api-client.js`, com endpoints isolados em `server/erp-finance-router.js`.

**Tech Stack:** Node.js >=22, CommonJS no PDV, SQLite, Electron 39, Playwright 1.63, Node test runner, `@artisys/finance-domain` 0.1.0 vendorizado/pinado.

**Spec:** `docs/superpowers/specs/2026-09-23-erp-p0-p3-design.md`

## Global Constraints

- Não duplicar EventBus, outbox, auditoria, RBAC, backup/restore, módulos ou importador CSV/XLSX existentes.
- Não substituir `js/domains/finance/finance-service.js`; estender sem quebrar contratos existentes.
- Reusar conceitos/lógica madura de `sistemafinanceiro`, adaptados ao PDV.
- Reusar `@artisys/finance-domain` para fingerprints, classificação e sugestões de conciliação.
- Toda mutação sujeita a retry precisa de idempotência persistida.
- Importar extrato nunca liquida conta automaticamente; vínculo/baixa só após ação explícita.
- Core local-first, sem serviço pago obrigatório.
- Migrations somente incrementais e preservando instalações existentes.
- Todo recurso novo precisa de unit/integration test, E2E Electron real, registro no `qa/artisys-qa.config.json` e inclusão em `full` e `release.criticalFlows`.
- `npm run verify` e `npm run verify:release` precisam ficar verdes antes da conclusão.

## Review Focus

1. **OFX duplicado vs. pagamentos legítimos repetidos:** mesma ocorrência não duplica; dois PIX iguais com FITIDs/linhas diferentes coexistem. Teste na Task 8.
2. **Datas/fuso/fim de mês:** datas de negócio não podem deslocar um dia; recorrência em dia 31 deve ajustar para o último dia do mês. Testes nas Tasks 4 e 11.
3. **Restart durante recorrência:** gerar, reiniciar e gerar novamente não pode criar segunda ocorrência. Teste na Task 11 e E2E da Task 13.
4. **Baixa parcial + estorno:** DRE por caixa deve refletir somente settlements ativos e voltar ao valor correto após reversão. Teste na Task 4.
5. **Alertas derivados:** marcar/ocultar alerta não pode alterar saldo, lançamento ou projeção. Teste na Task 12.
