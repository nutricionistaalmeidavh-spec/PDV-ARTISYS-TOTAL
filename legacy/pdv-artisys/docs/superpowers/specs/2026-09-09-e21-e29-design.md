# PDV ArtiSys — E21–E29 Design

## Status

Design aprovado em conversa em 2026-09-09. Esta especificação fecha o produto do estágio operacional E20 até o release comercial 1.0, mantendo o requisito central: **desktop + rede local, sem SaaS e sem dependência de internet para a operação diária**.

## Objetivo

Completar robustez LAN, backup/restore, configurações, importação/migração, segurança/observabilidade, QA operacional, empacotamento Windows, piloto e release 1.0 sem reescrever o núcleo E01–E20.

## Princípios não negociáveis

- SQLite continua sendo acessado exclusivamente pelo servidor autoritativo.
- Terminais nunca recebem acesso SQL nem caminho direto para o arquivo do banco.
- Dinheiro permanece em centavos inteiros.
- Movimentos de estoque/caixa e auditoria permanecem históricos/imutáveis.
- EventBus + outbox continuam sendo a fronteira de efeitos derivados.
- Comandos LAN mutáveis usam `mutationId`/idempotência.
- Renderer continua isolado por preload/IPC estreito.
- Credenciais fiscais permanecem fora do renderer e protegidas pelo sistema operacional.
- Migrations são incrementais, versionadas e não destrutivas.
- Backup deve ser validado antes de ser considerado utilizável.
- Restore nunca sobrescreve o banco ativo sem snapshot de segurança e validação.
- Nenhuma funcionalidade simulada pode ser apresentada como operacional no release 1.0.

## Reuso confirmado

### PDVNexus

O `windows-10/apps/nexus-desktop/main.cjs` já contém padrões úteis para:

- servidor HTTP local;
- identificação de banco no `userData`;
- diretórios de backup;
- retenção de backups;
- snapshot pré-migração;
- settings persistentes;
- bridge Electron e periféricos;
- single-instance lock.

Esses padrões serão **adaptados**, não copiados literalmente. Não reutilizar:

- reset destrutivo de dados ao mudar a versão instalada;
- CORS `*`;
- snapshot JSON como fonte primária de verdade;
- qualquer exposição genérica de filesystem/serial ao renderer.

### PDV ArtiSys E01–E20

Reutilizar diretamente:

- servidor local `/api/v1`;
- `createPdvRuntime`;
- migrations e SQLite atual;
- autenticação/sessões e RBAC;
- EventBus/outbox/effect store;
- hardware adapters;
- fila de impressão;
- bridge fiscal segura;
- auditoria sanitizada;
- shell Electron e design system atual.

# E21 — LAN robusta

## Objetivo

Permitir vários terminais confiáveis na mesma rede local com um único servidor autoritativo.

## Componentes

### `server/lan/terminal-registry.js`

Responsável por registrar terminais autorizados.

Dados persistidos por terminal:

- `terminal_id`;
- nome amigável;
- fingerprint/installation id;
- status `ACTIVE|BLOCKED`;
- versão do app;
- última conexão;
- data do pareamento;
- usuário que autorizou.

### Pareamento

Fluxo:

1. servidor gera código temporário de pareamento;
2. terminal informa o código;
3. servidor registra a identidade do terminal;
4. servidor retorna credencial local específica do terminal;
5. credencial fica protegida no desktop cliente;
6. pedidos seguintes identificam terminal + sessão do usuário.

Código temporário deve expirar e ser single-use.

### Compatibilidade de versão

Handshake retorna:

- versão do servidor;
- versão mínima de terminal suportada;
- schema version;
- capabilities.

Versão incompatível bloqueia comandos mutáveis, mas pode permitir diagnóstico/upgrade.

### Reconexão

O cliente implementa estados:

`CONNECTING → ONLINE → DEGRADED → OFFLINE → RECONNECTING`.

Não haverá fila offline de vendas nesta versão 1.0. Se o servidor central não estiver acessível, o terminal entra em modo somente diagnóstico e não confirma operações que dependem do estado compartilhado.

### Concorrência

- toda mutação relevante recebe `mutationId`;
- o servidor persiste deduplicação de mutations críticas;
- conclusão/cancelamento de venda revalida estado dentro da transação;
- abertura de caixa respeita unicidade por política configurada;
- comandos duplicados retornam o resultado canônico anterior quando seguro.

# E22 — Backup e recuperação

## Objetivo

Garantir recuperação local consistente do banco e configurações críticas.

### Backup manager

Novo módulo `js/core/backup/backup-service.js`.

Operações:

- `createBackup(reason)`;
- `listBackups()`;
- `validateBackup(id)`;
- `restoreBackup(id)`;
- `pruneBackups()`;
- `getBackupStatus()`.

### Conteúdo

Cada backup deve possuir:

- arquivo SQLite consistente;
- manifesto JSON;
- app version;
- schema version;
- createdAt;
- reason;
- SHA-256 do arquivo;
- tamanho;
- status de validação.

### Política padrão

- automático diário;
- pré-migration;
- pré-restore;
- manual pelo administrador;
- retenção configurável, padrão 30 arquivos.

### Restore

Restore exige papel `admin` e segue:

1. validar backup selecionado;
2. criar backup `pre-restore` do banco ativo;
3. fechar conexões;
4. restaurar em arquivo temporário;
5. abrir e rodar `PRAGMA integrity_check`;
6. conferir schema compatível;
7. substituir banco ativo atomicamente;
8. reiniciar runtime;
9. registrar auditoria.

Se qualquer etapa falhar, o banco ativo anterior é preservado.

# E23 — Configurações

## Objetivo

Transformar Configurações em módulo operacional central.

### Persistência

Tabela `app_settings` por chave tipada e escopo.

Categorias:

- empresa/loja;
- terminal;
- LAN;
- caixa;
- impressão;
- hardware;
- fiscal público;
- backup;
- segurança;
- comportamento da UI.

Segredos não ficam em `app_settings`; continuam em stores protegidos no processo principal.

### UI

Tela com seções e status reais:

- Geral;
- Rede e terminais;
- Caixa;
- Hardware;
- Impressão;
- Fiscal;
- Backup;
- Usuários e segurança;
- Sobre/versão.

Alterações críticas exigem `admin` ou `manager` conforme categoria e geram auditoria.

# E24 — Importação e migração

## Objetivo

Implantar clientes existentes sem redigitação.

### Formatos

Primeira versão suporta CSV UTF-8 e XLSX através de módulo isolado de importação. CSV é o formato obrigatório para funcionamento base; XLSX é conveniência adicional.

### Fluxo

`arquivo → parser → normalização → preview → validação → commit transacional → relatório`.

### Tipos

- produtos;
- categorias;
- clientes;
- fornecedores;
- estoque inicial.

### Regras

- preview obrigatório antes do commit;
- erros por linha;
- SKU/barcode/documento normalizados;
- política explícita `CREATE|UPDATE|SKIP` para colisões;
- import batch id persistido;
- reprocessar o mesmo batch não duplica registros;
- estoque inicial entra pelo InventoryService como movimento `opening`/ajuste, nunca por update direto de saldo.

# E25 — Segurança e observabilidade

## Objetivo

Tornar o produto diagnosticável e auditável em campo.

### Auditoria

Tela somente leitura para admin/manager com filtros por:

- data;
- usuário;
- terminal;
- ação;
- entidade.

Dados sensíveis continuam sanitizados.

### Logs

Novo logger estruturado local com:

- nível;
- timestamp;
- subsystem;
- correlation id/mutation id;
- terminal;
- mensagem sanitizada.

Nunca registrar senha, token fiscal, credenciais LAN ou payload fiscal sensível completo.

### Health detalhado

`/api/v1/system/health` autenticado retorna:

- banco;
- schema;
- outbox pendente;
- efeitos com falha;
- espaço em disco;
- backup mais recente;
- versão servidor;
- terminal count;
- fila de impressão;
- documentos fiscais pendentes/falhos.

### Pacote de diagnóstico

Administrador pode gerar ZIP local contendo apenas:

- manifesto do sistema;
- logs sanitizados;
- health snapshot;
- versões;
- configuração pública;
- lista de migrations.

Não incluir banco, senhas, tokens ou credenciais fiscais por padrão.

# E26 — QA operacional

## Objetivo

Transformar a suíte atual em gate de Release Candidate.

### Testes obrigatórios

- regressão E01–E25;
- duas vendas concorrentes do mesmo estoque;
- double-submit de conclusão;
- dois terminais no mesmo servidor;
- reconexão após queda;
- restart com outbox pendente;
- impressão falha → retry;
- fiscal falha → retry;
- devolução parcial concorrente;
- fechamento de caixa com divergência;
- backup → corrupção simulada → rejeição;
- backup válido → restore;
- migration a partir de banco anterior;
- import repetido sem duplicação;
- permissões API/IPC;
- renderer sem acesso Node/SQL/filesystem genérico.

### Gates

`npm run verify` deve executar unit + integration + architecture checks.

Adicionar `npm run verify:release` para testes mais pesados de concorrência/recovery/package smoke.

# E27 — Instalador e atualização

## Objetivo

Produzir instalação comercial Windows reproduzível.

### Perfis

O instalador suporta:

- **Servidor + Terminal**: máquina principal, banco e serviço local;
- **Terminal**: cliente que pareia com servidor existente.

### Dados

Dados ficam fora do diretório de instalação, no `userData`/diretório de dados dedicado, para atualização nunca substituir banco/backups/credenciais.

### Empacotamento

Usar Electron Builder (ou empacotador equivalente compatível com a base atual) para:

- instalador Windows x64;
- ícone/metadados ArtiSys;
- atalho;
- desinstalação sem apagar dados por padrão;
- artefato versionado.

### Atualização

A v1.0 não depende de auto-update remoto para operar. Estratégia inicial:

1. baixar/obter instalador assinado por canal de distribuição;
2. backup pré-update;
3. instalar nova versão;
4. migrations incrementais;
5. smoke check;
6. rollback operacional via versão anterior + backup quando necessário.

Nenhum reset de banco por mudança de versão.

# E28 — Piloto e diagnóstico de campo

## Objetivo

Preparar e registrar uma implantação real controlada.

### Wizard/checklist

- identificar servidor;
- cadastrar loja;
- cadastrar terminal;
- testar LAN;
- testar impressora;
- testar gaveta;
- testar balança quando aplicável;
- configurar fiscal quando aplicável;
- executar backup manual;
- venda teste;
- cancelamento/devolução teste;
- fechamento de caixa teste;
- gerar diagnóstico.

### Evidência

A entrega inclui checklist persistido e relatório de prontidão, não exige que exista um estabelecimento externo disponível durante o desenvolvimento.

Estados:

`NOT_STARTED | IN_PROGRESS | READY | BLOCKED | BLOCKED_EXTERNAL`.

`BLOCKED` indica falha interna que precisa ser corrigida antes da implantação. `BLOCKED_EXTERNAL` representa dependência externa indisponível — por exemplo, credenciais fiscais reais ou hardware não presente — e nunca é apresentado como aprovado.

# E29 — PDV ArtiSys 1.0

## Objetivo

Fechar o release comercial.

### Release manifest

Gerar manifesto contendo:

- versão;
- commit;
- schema version;
- data do build;
- artefatos;
- checksums;
- resultado `verify` e `verify:release`;
- lista de capabilities;
- limitações externas conhecidas.

### Documentação

- instalação servidor;
- instalação terminal;
- pareamento;
- abertura/fechamento de caixa;
- venda/devolução;
- backup/restore;
- configuração de impressora/hardware;
- configuração fiscal;
- importação;
- diagnóstico e suporte;
- atualização.

### Critério de release 1.0

A versão pode ser marcada 1.0 quando:

1. E01–E29 estiverem integradas no `main`;
2. `npm run verify` estiver verde;
3. `npm run verify:release` estiver verde no ambiente suportado;
4. pacote Windows for gerado com sucesso no CI Windows;
5. nenhum placeholder funcional permanecer nas telas do produto;
6. backup/restore e migration smoke estiverem verdes;
7. instalação Servidor+Terminal e Terminal tiver smoke automatizado onde possível;
8. checklist de piloto puder ser concluído ou marcar dependências externas explicitamente;
9. emissão fiscal real continuar bloqueada até configuração válida do cliente.

## Modelo de dados adicional

Migrations E21–E29 devem adicionar, quando necessárias:

- `terminals`;
- `pairing_codes`;
- `processed_mutations`;
- `app_settings`;
- `backup_records`;
- `import_batches`;
- `import_errors`;
- `system_logs` ou retenção equivalente;
- `pilot_checks`.

Todas as tabelas novas seguem migrations idempotentes e não destrutivas.

## APIs novas

Famílias previstas:

- `/api/v1/lan/*`;
- `/api/v1/terminals/*`;
- `/api/v1/backups/*`;
- `/api/v1/settings/*`;
- `/api/v1/imports/*`;
- `/api/v1/audit/*`;
- `/api/v1/system/*`;
- `/api/v1/pilot/*`.

Endpoints administrativos exigem RBAC no servidor.

## Tratamento de falhas

- falha LAN nunca grava estado parcial no terminal;
- falha de backup não apaga backup anterior;
- restore inválido não toca no banco ativo;
- import inválido não aplica lote parcial salvo quando modo atômico estiver ativo;
- incompatibilidade de versão bloqueia mutações;
- falha de hardware/fiscal permanece diagnosticável e retryable sem invalidar a venda canônica;
- diagnóstico nunca exporta segredos.

## Fora de escopo da v1.0

- SaaS;
- sincronização em nuvem;
- operação multi-filial pela internet;
- venda offline em terminal desconectado do servidor central;
- auto-update obrigatório por serviço remoto;
- TEF homologado específico sem contrato/SDK do adquirente;
- emissão fiscal em produção sem credenciais e dados tributários reais;
- app mobile.

## Estratégia de implementação

Ordem obrigatória:

**E21 LAN → E22 Backup → E23 Configurações → E24 Importação → E25 Segurança/observabilidade → E26 QA → E27 Packaging → E28 Piloto → E29 Release.**

Cada entrega entra por TDD, mantendo a suíte anterior verde. Desenvolvimento ocorre em `feat/e21-e29`; `main` só recebe o bloco após verificação final e merge explícito.
